# 개발 계획

기준: [PRD](../PRD.md). 사용자 승인 이후 문서를 먼저 커밋하고 단계별로 구현한다. 이 문서는 전체 PoC 계획이며 기능 구현 완료를 의미하지 않는다.

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| 1 | PRD·기술·API·평가 설계 | 요구사항 ID, 기본 결정, 테스트 연결 및 선행 문서 커밋 |
| 2 | Python 3.12·FastAPI·설정·DB·테스트 환경 | 잠긴 의존성으로 설치, 서버 준비 상태, 실제 PostgreSQL 트랜잭션 검사 |
| 3 | 로그인·복수 Role·데이터 권한·승인·감사 | 비밀번호 해시, 현재 권한 확인, 취소·중복·권한 회수 테스트 |
| 4 | 온톨로지 정의·버전·매핑·Neo4j | 편집/조회 API, 원천 추적, 참조/중복 검사, 실제 그래프 질의 |
| 5 | PDF·Excel·HWP·RAG·Wiki | 지원 범위 검증, 권한 검색·출처·Hit, 문서 갱신/삭제 |
| 6 | Groq·Chat·LangGraph·대화 맥락 | 구조화 의도 추출, 도구 허용 목록, 실제 모델 질의와 오류 검사 |
| 7 | 재고 부족·내부 알림·승인·발주 초안 | 최신 상태 재검증, 대표 흐름 및 중복 방지 |
| 8 | 관리 API 통합·화면 계약·PoC 평가 | 실행 안내, API 명세, 테스트/실제 모델 평가 결과, 남은 한계 |

## 첫 개발 묶음

단계 1~3을 우선 구현한다. Groq 어댑터와 Chat의 구조화 의도·권한 판단 골격을 함께 마련해 모델과 서버 권한 검증의 경계를 테스트한다. 온톨로지/RAG/발주 도구가 아직 연결되지 않았다면 해당 업무를 완료했다고 응답하지 않는다. 단계 4~8은 뒤따르는 개발 묶음이며 미구현 API를 성공 응답으로 위장하지 않는다.

## 기술 불확실성

- Groq 모델 ID는 계정의 실제 제공 목록과 한국어·구조화 출력 검사 후 확정한다. 기본 후보는 설정으로 교체 가능하다.
- Cloud 실제 호출은 안전한 `GROQ_API_KEY` 주입과 `api.groq.com` 접근이 선행되어야 한다. 대역 검증과 구분한다.
- HWP 파서·표 추출·스캔 PDF 지원은 대표 파일로 검증한다. 지원되지 않는 파일은 명시적 오류를 반환한다.
- SAP 실제 키·단위·변경 이벤트는 승인된 샘플로 확인한다. 합성 데이터 검증은 실제 연동 검증을 대신하지 않는다.
- 임베딩은 별도 로컬 모델 또는 승인된 제공자가 필요하다. Groq 채팅 API를 임베딩 API로 가정하지 않는다.

## 작업 방식

기대 행동 → 실패 테스트 → 구현 → 통과 → 실제 연결 검사 순서로 진행한다. 모델 경계는 대역으로 재현하되 권한·승인·DB는 실제 로직을 검사한다. 단계별 검증 후 커밋하고 구현 상태를 별도 기록한다. 시간 추정은 초기 연결·모델·파서 검증 이후 정한다.
