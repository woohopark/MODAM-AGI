# MODAM-AGI — 공통 업무 에이전트 플랫폼 PoC

## 1. 목표와 범위

Chat으로 업무를 정확하고 신속하게 처리하는 공통 에이전트 플랫폼이다. 사용자의 업무 의도·맥락·Role을 파악하고 회사 규정과 기업 데이터의 관계를 근거로 답변·분석·후속 업무 제안·승인된 실행을 수행한다. 처음 보는 목표에 대해서도 허용된 도구로 계획·수행·검증·재계획한다. 기술 도입 자체를 범용 AGI 달성으로 주장하지 않는다.

화면은 별도 저장소에서 개발한다. 이 저장소는 에이전트, 서버 API, 데이터·모델 연결, 승인·실행·감사 기록에 집중한다. 화면에서 관리할 항목의 요청·응답·오류·이벤트 계약은 제공한다.

초기 LLM은 **Groq Cloud API**를 사용한다. 로컬 모델이 없는 현재 환경에서 Ollama 설치를 선행 조건으로 두지 않는다. 모델 ID는 설정으로 지정하고 실제 제공 여부를 확인한다. Local/Cloud 공통 인터페이스는 유지한다. API 키는 `GROQ_API_KEY`로 주입하고 소스·문서·로그·Git에 저장하지 않는다.

## 2. 초기 범위와 기본 결정

- 한 업무 영역의 객체·관계 유형 각각 3~5개와 승인된 수백~수천 건 샘플을 범위 가이드로 사용한다.
- 창고·물품·재고·발주의 연결을 대표 사례로 사용한다. 실제 SAP 제품·키·테이블은 제공 데이터 확인 후 정한다.
- 원천은 읽기 전용으로 취급한다. 승인된 비식별 추출 파일로 시작할 수 있다. 합성 데이터와 실제 기업 데이터 검증 결과를 구분한다.
- 발주는 **발주서 초안 작성까지**, 알림은 **플랫폼 내부 알림**, Wiki는 **Admin 선택 생성**을 초기 기본안으로 삼는다.
- 실시간 SAP 연동, ERP 쓰기, 전사 온톨로지, 무검토 자동 구축, 모든 문서 변형 지원, 운영 SLA는 후속 단계다.
- 외부 Cloud 전송에는 허용된 입력만 사용한다. Groq 사용 승인이 모든 기업 자료의 외부 전송 허가를 의미하지 않는다.

## 3. 사용자·Role·권한

| ID | 요구사항 |
|---|---|
| AUTH-01 | Admin은 고유 ID·비밀번호·하나 이상의 Role로 사용자를 생성한다. 비밀번호는 안전하게 해시한다. |
| AUTH-02 | Admin은 Role 생성 및 사용자의 Role 추가·해제를 수행한다. 한 사용자에 복수 Role을 허용한다. |
| AUTH-03 | Role은 업무별 조회·제안·작성·실행·승인 권한과 데이터 접근 범위를 갖는다. |
| AUTH-04 | 로그인 후 서버가 사용자·현재 Role을 실행에 전달한다. Chat으로 주장한 신분은 권한을 바꾸지 않는다. |
| AUTH-05 | 도구 호출과 승인 후 실행 직전에 현재 권한을 확인한다. 역할 명칭이나 LLM 판단만으로 허용하지 않는다. |
| AUTH-06 | 거절 시 제한 데이터와 도구 결과를 노출하지 않는다. 가능한 범위에서 이유를 설명한다. |

초기 권한 정책은 복수 Role의 명시적 허용 합집합으로 한다. 데이터 범위는 업무 권한과 함께 검사한다. 명시적 거부 우선 정책은 후속 확장 시 별도 정의한다. 업무 승인자는 Role 권한으로 표현하고 별도 계정 유형을 강제하지 않는다.

## 4. Chat 에이전트

| ID | 요구사항 |
|---|---|
| AGENT-01 | 의도·대상 객체·수량·단위·조건·기대 결과를 추출한다. 필수 정보가 없거나 모호하면 질문한다. |
| AGENT-02 | 같은 대화의 입력·결과·승인 맥락을 참조하며 이전 사실을 최신 상태로 가정하지 않는다. |
| AGENT-03 | 허용 도구로 계획을 구성하고 실제 결과를 검증한다. 실패·상태 변화 시 재계획하거나 중단한다. |
| AGENT-04 | 변경 작업은 대상·내용을 제시하고 필요한 승인을 받는다. 승인 내용 변경 시 다시 확인한다. |
| AGENT-05 | 완료·승인 대기·거절·실패·결과 불명을 구분하고 재시도·후속 요청의 중복 실행을 방지한다. |
| AGENT-06 | 응답 시간과 단계별 시간을 측정한다. 초기에는 측정된 근거 없이 고정 성능 목표를 약속하지 않는다. |

## 5. 온톨로지·Knowledge Graph·기업 데이터

| ID | 요구사항 |
|---|---|
| ONT-01 | ERP·MES·SAP 또는 승인된 추출 파일을 공통 형식으로 변환하고 원천 키·단위·갱신 시점을 보존한다. |
| ONT-02 | 객체 유형·속성·관계 방향·다중성·제약과 원천 매핑을 정의한다. 정의와 실제 데이터 객체를 구분한다. |
| ONT-03 | Admin이 API로 정의를 추가·수정·검토하고 정의/실체 그래프를 조회한다. 버전·변경 이유·검토자를 기록한다. |
| ONT-04 | 승인된 정의로 그래프를 적재하고 중복·누락·참조 오류를 검사한다. 같은 입력 재적재는 중복을 만들지 않는다. |
| ONT-05 | 문제 객체에 연결된 객체·업무를 탐색하고 근거 경로를 제시한다. 관계 연결만으로 인과관계를 확정하지 않는다. |
| ONT-06 | 반자동 정의·매핑 후보는 근거와 함께 사람이 검토한다. 미검토 LLM 추정을 사실로 적재하지 않는다. |

방법론: 업무 질문 → 원천 조사 → 개념·속성·관계 정의 → 원천 매핑 → 사람 검토 → 샘플 적재 → 질문 검증. 용어집·정의서·매핑표·변경 기록을 관리한다.

## 9. 대표 시나리오

### A. 권한 없는 발주

회계 담당자가 로그인하고 “창고 B 물품 100건을 발주해 줘”라고 요청한다. 서버는 실제 발주 권한을 검사한다. 권한이 없으면 발주 도구를 실행하지 않고 이유를 안내한다. 권한이 있다면 역할 이름만으로 거절하지 않는다. “100건”의 대상·단위가 불명확하면 추가 질문한다.

### B. 회사 규정 질의

사용자 질문 → 접근 가능한 문서 검색 → 조항·적용 범위 확인 → 근거 위치를 포함한 답변 → 검색·컨텍스트·인용 지표 기록. 없는 근거를 만들어 답하지 않는다.

### C. 재고 부족과 후속 발주

출고 반영 → 최신 재고 확인 → 창고·재고·물품·발주 관계 탐색 → 기준과 기존 발주 확인 → 문제·발주 제안 알림 → 권한 있는 사용자 승인 → 상태 재확인 → 발주서 초안 작성. 출고량만으로 잔여 재고나 발주 수량을 추정하지 않는다.

## 10. PoC 성공 기준

| 평가 | 통과 기준 |
|---|---|
| 인증·권한 | 복수 Role 로그인, 허용·거절 사례 실행. 제한 데이터 노출 및 거절된 업무 실행 없음 |
| 온톨로지·매핑 | 평가 질문에 필요한 정의 검토. 레코드·관계 각각 고정 표본 10건 중 8건 이상 원천과 일치 |
| 문서·RAG | PDF·Excel·HWP 각 대표 샘플 적재·검색·출처 확인. 질문 7개 중 5개에서 핵심 사실과 근거 정확 |
| 한계 처리 | 정보 부족·권한 거절·상충 근거 각 1개에서 적절히 질문·거절·충돌 안내 |
| 전체 흐름 | 관계 기반 문제 탐색부터 내부 알림·승인·초안까지 대표 사례 1개 실제 실행 |
| 반복 처리 | 같은 입력 재적재 및 요청·이벤트 재시도에서 중복 객체·관계·초안 없음 |
| 모델·관측 | 준비된 제공자의 실제 설정 적용 검증. 로그·근거·승인·Hit·시간 조회 가능 |

평가 전에 질문·기대 결과·데이터 버전을 고정한다. 대역 테스트·합성 데이터·실제 모델·실제 ERP 검증을 구분하며 미실행을 통과로 표시하지 않는다. 반자동 후보 채택률·검토 시간·응답 시간은 우선 측정하고 탈락 조건으로 두지 않는다. 권한·승인 원칙은 완화하지 않는다.
